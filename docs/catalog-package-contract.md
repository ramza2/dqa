# Catalog Package v2 Consumer Contract

## 1. Purpose

This document defines how DQA consumes the finalized Catalog Package generated by DEMIS Schema Analyzer.

The producer remains the authority for package generation.
DQA validates and imports the package; it does not rewrite it.

## 2. Supported package identity

Expected:
- package_format: `demis-catalog-package`
- package_version: `2.x`

Version handling must be explicit.
Unsupported major versions must be rejected.

## 3. Expected ZIP structure

The finalized package currently contains the following logical structure:

```text
demis_catalog_package/
  manifest.json
  database.json
  categories.json
  tables.json
  columns.json
  relations.json
  indexes.json
  erd.json
  PACKAGE_README.md

  analysis/
    latest_run.json
    schema_snapshot.json

  validation/
    preflight.json

  diff/
    latest.json
    latest_summary.md

  reports/
    *.docx
```

The exact manifest is authoritative for managed files.

DQA must not assume that every supplemental human-readable artifact is required for runtime execution.
Core catalog/runtime requirements should be defined in validation code.

## 4. Import validation sequence

1. Confirm ZIP is readable.
2. Locate expected package root.
3. Parse `manifest.json`.
4. Validate package format.
5. Validate supported package version.
6. Validate every manifest-managed path exists exactly once.
7. Verify each declared SHA-256.
8. Reject path traversal, duplicate ZIP entries, excessive file counts, excessive uncompressed size, and zip-bomb style expansion.
9. Parse required JSON files.
10. Validate source identity and schema fingerprint.
11. Evaluate package readiness.
12. Persist import metadata and immutable file-derived records.

Do not extract files using unsafe paths.

## 5. Readiness

Producer readiness values:
- READY
- WARNING
- BLOCKED

Initial DQA policy:
- READY: import + activation allowed
- WARNING: import allowed for inspection; activation is prohibited
- BLOCKED: import may be retained for diagnostics; activation is prohibited

A future WARNING override must be a deliberate reviewed product/security change rather than an implicit operator shortcut.

## 6. Core metadata mapping

### database.json

Use for:
- source name
- DB type
- database/service identity
- default schema
- latest analysis metadata
- exported security flags

Never expect live credentials in this file.

### tables.json

Use for:
- schema/table identity
- type
- DB comment
- object fingerprint
- key constraints
- category references

### columns.json

Use for:
- table/column identity
- ordinal
- type details
- nullable/default
- DB comment
- PK/unique flags
- object fingerprint

### relations.json

Use for:
- FK identity
- source table
- target table
- ordered column mapping
- object fingerprint

### indexes.json

Use for:
- index identity
- uniqueness
- method/definition when provided
- ordered columns
- object fingerprint

### categories.json

Treat as semantic metadata separated from physical DB facts.

Retain assignment provenance such as MANUAL/AUTO/IMPORT when provided.

### erd.json

Use for visualization/navigation.
Do not make it the sole source of truth when the normalized catalog files contain richer details.

## 7. Supplemental metadata

### analysis/latest_run.json

Use for:
- latest successful run identity
- target schema
- counts
- fingerprint
- timestamps

### analysis/schema_snapshot.json

Use for:
- physical snapshot traceability
- future package/version comparison
- consistency diagnostics

### validation/preflight.json

Use for:
- producer-side database analysis readiness evidence

Do not treat this as live DQA connection validation.
DQA will still require its own live read-only connection test before query execution.

### diff/latest.json and latest_summary.md

Use as informational change context.

Do not infer that absence of diff means the schema has never changed.

### reports/*.docx

Human-readable artifact only.
Do not parse DOCX as the canonical runtime catalog source.

## 8. Immutable import revision

Each successful import should create an immutable revision with at least:
- internal import ID
- source identity
- package format/version
- generated_at
- imported_at
- original archive SHA-256
- manifest SHA-256
- schema fingerprint
- readiness
- validation status
- original file metadata
- activation status/history

Never overwrite a previous revision because a new package has the same source name.

Live DEMIS connection configuration is not part of this package.
DQA must bind an imported source to a separately managed Connection Profile before query execution.

## 9. Security

Do not expect or accept credentials from the package.

If suspicious secret-like fields appear:
- do not use them
- flag validation warning/error according to policy
- never echo them into logs

Package validation logs should use file names, digests and structural errors, not raw secret-looking values.

## 10. Future compatibility

Minor 2.x additions should be tolerated when safe and explicitly modeled as optional.

A major version change requires a reviewed adapter/contract update.
